# 拆、复制、加速：九大架构模式与性能的四把尺

> 读完李智慧《大型网站技术架构》第 2 章，最大的收获不是九个名词，而是一句翻译：**模式是解题工具，要素是考试科目——架构设计就是用工具箱换成绩**。这篇是总账，每一式都拿我维护的一套真实 MES（按业务拆成 9 个微服务、MySQL + Redis 单实例部署的企业系统）对照过。

## 一、先给一张总图：九式归三族

九个模式背下来很难，归成三族一眼就懂：

```
拆（把大变小）     复制（把一变多）    加速与治理
├─ 分层（横向切）  ├─ 集群（服务多份） ├─ 缓存
├─ 分割（纵向切）  └─ 冗余（数据多份） ├─ 异步
└─ 分布式（拆完上多机）              ├─ 自动化
                                    └─ 安全
```

## 二、九式逐个过

### 1. 分层（横向切）

**切的是技术职责**：应用层 → 服务层 → 数据层；每天写的 Controller → Service → Dao 就是它，OSI 七层是祖师爷。

- 买的不是性能，是**改动隔离**——换数据库只动数据层
- 三条纪律：只相邻层调用、禁跨层（Controller 直写 SQL 就是跨层）、下层不反调上层
- 代价：层间调用开销，层不能无限切细

### 2. 分割（纵向切）

**切的是业务边界**：商品、订单、库存各成模块，高内聚低耦合。和分层正交——横向按职责、纵向按业务，合起来是棋盘（我们的 MES 横向是 C/S/D 三层，纵向是 9 个业务服务）。**分割是分布式的前提**：先切出独立单元，才谈得上独立部署。

### 3. 分布式（拆完放到多台机器）

分层分割出的单元部署到多台服务器，通过网络协作对外表现为一个系统。

- 买：突破单机容量、独立扩容、故障隔离
- 代价：方法调用变网络调用——**会慢、会超时、会挂**；数据一致性问题；一笔业务穿 5 个服务，排障像破案
- 微服务是分布式在应用层的具体形态（按业务拆 + 独立部署 + 库私有 + 轻量通信）。**拆的那一刻就签收分布式的全套账单**：超时、重试、幂等、分布式事务——我们系统里的 Redis 分布式锁，就是这张账单上最早寄到的一张（参见[上一篇](/posts/system-design/redis-distributed-lock-deep-dive)）

### 4. 集群（每个单元多复制几份）

同一个模块部署多份 + **负载均衡器**统一对外。和分布式的关系是最容易混的一对：

> **集群是"同一件事雇多个人干"（复制），分布式是"一件大事拆给不同人干"（分工）。** 集群买可用性，分布式买扩展性。

- **没有负载均衡的多份副本不是集群，是浪费**——upstream 是集群的调度员
- 完整形态是乘法：拆成 N 块（分布式）× 每块 M 份（集群）× 数据主从（冗余）
- 试金石两问：机器上装的程序一样吗（一样→集群）？随便挂一台系统还完整吗（完整→有冗余）？

补充一个部署账：机器少、服务多时，**把每个服务的副本打散到所有机器**（每台跑全部服务、端口区分），任何一台挂全部服务还活着——用 3 台机器给 9 个服务都上集群，比专机专用便宜 9 倍。虚拟机和 Docker 让这种"合宿"有了安全边界（内存配额、故障不传染），K8s 是它的自动化版。

### 5. 缓存（数据放得离使用者更近）

四种形态从远到近：CDN → 反向代理 → 本地缓存 → 分布式缓存（Redis）。**两个前提**：①访问热点不均衡（二八定律）②数据有时效可过期——不满足就只有一致性的痛、没有加速的爽。命门是脏数据，判据是"丢了能重建的才敢缓存"。

缓存自己变成集群时，路由算法是关键，三代演进：

| 方案 | 思路 | 3→4 台时伤害 |
|---|---|---|
| 取模 `hash%N` | 简单，机器数焊死在公式里 | **3/4 key 换位** 💥 |
| 一致性哈希 | 2³² 环 + 虚拟节点 | ~1/4（1/N），隐式 |
| hash slot（Redis Cluster） | CRC16%16384 定槽，**槽是迁移单位** | 只动被迁的槽 |

hash slot 的精髓是**两层拆分**：key→槽（天规，永不改变）+ 槽→节点（可编辑的配置表）。取模的病根是加机器等于改宪法全体重算；slot 把数据分布从概率问题变成了配置管理问题。

顺带记住**缓存雪崩**（miss 率瞬间飙升打穿数据库）的三个成因：大量 key 同时过期 / 缓存宕机重启 / 路由重分布。

### 6. 异步（扔进队列就走）

调用方发消息立刻返回，接收方自己消费。四个收益：

| 收益 | 说明 |
|---|---|
| 解耦 | 生产者不知道消费者存在，加订阅者零改动 |
| 提速 | 不等对方干完 |
| 削峰 | 高峰进队列排队，消费端按自己的节奏消化 |
| 失败隔离 | 消费者挂了生产者照常（对比同步 API 的可用性耦合） |

代价：结果有延迟、排障链路长、**必须幂等**。口诀：**要结果就等（同步），要办事就喊（异步）**。消息队列不是分布式服务的组成部分——服务间"拿结果"走同步 RPC，"发通知"走事件广播，两条并行通道，我们的系统两样都在用（Dubbo 管前者、Redis 频道管后者）。

### 7. 冗余（数据多存几份）

和集群一字之差：**集群复制的是服务，冗余复制的是数据**。阶梯：冷备 → 热备（主从）→ 双机房 → 两地三中心。读写分离、binlog 订阅同步全站在主从复制上。

**优先级高于集群**：服务挂了可以重启，数据丢了无法重生。衡量指标是几个 9：

| 可用性 | 年宕机 |
|---|---|
| 99% | 87.6 小时（有单点的裸奔态） |
| 99.9% | 8.8 小时 |
| 99.99% | 52.6 分钟（大站目标，需自动转移） |
| 99.999% | 5.3 分钟（电信金融级） |

### 8. 自动化（人退脚本进）

链条：构建 → 测试 → 发布 → 监控告警 → 自动故障转移。动因：规模一大，人工 = 慢 + 贵 + 易错。本质是**把运维知识从人脑写进脚本**——人脑会离职会忘会手抖，脚本只会重复执行。

### 9. 安全（假设会被攻击）

三类手段：认证（你是谁）/ 加密（防偷看篡改）/ 防护（验证码、防 XSS、SQL 注入、限流、风控）。原则两条：默认最小权限 + 纵深防御。安全是成本不对称的生意——**攻破你的成本大于攻破你能得到的收益，就及格了**。

## 三、性能的四把尺

第 3 节讲架构五要素（性能/可用/伸缩/扩展/安全），性能这一科用四把尺打分：

### 尺 1：响应时间（RT）

一个请求从发出到收到响应的耗时。用户感知的分界线：**1 秒内流畅，3 秒焦躁，10 秒走人**。优化时通常看平均值和分位值（P95/P99——99% 的请求快过这个数；平均值会骗人，长尾才杀人）。

### 尺 2：并发数

同一时刻系统正在处理的请求数。注意三个口径：注册用户 ≠ 在线用户 ≠ 并发用户——压测和容量规划只认最后一个。

### 尺 3：吞吐量（TPS / QPS / HPS）

每秒完成的事务数 / 查询数 / HTTP 请求数。**它不是独立的第三把尺，而是前两把的乘积**——这就是著名的 Little 定律的工程版：

> **QPS ≈ 并发数 ÷ 平均响应时间**
>
> 例：100 个并发请求，每个平均 0.2 秒处理完 → 吞吐 ≈ 500 QPS。

这条公式反过来是性能分析的两条路：想提吞吐，要么**加并发**（扩容、加线程），要么**降 RT**（缓存、索引、异步）——九式里的缓存和集群正好各占一条路。

### 尺 4：性能计数器

System Load、CPU、内存、磁盘/网络 IO、线程数——**监控盯的就是这些**。它们不直接打分，但告诉你"分数为什么低"：RT 变慢时，是 CPU 饱了、IO 等待长了还是线程池满了，答案全在计数器里。

配套的还有四种测试姿势：**性能测试**（正常负载下验证指标）、**负载测试**（持续加压直到指标拐点，找容量上限）、**压力测试**（超过拐点继续压，看崩溃姿势和恢复能力）、**稳定性测试**（中等压力跑 7×24 小时，看内存泄漏这类慢性病）。

### 性能优化的给药位置：从外往里治

```
前端层：浏览器缓存 / gzip / CDN / 反向代理     ← 响应还没进机房就被解决
应用层：缓存 / 异步 / 集群 / 代码优化          ← 进了机房之后
存储层：缓存 / SSD / 读写分离 / NoSQL          ← 最里面那一跳
```

顺序有讲究：**前端和缓存层的一行配置，往往顶应用层重构一周**——gzip 一分钟纯赚，先摘低垂的果实再动手术。

## 四、模式 × 要素：工具箱怎么换成绩

五要素是成绩单，九式是换分的手段。另外记住本节最易混的一对辨析：

> **伸缩性（Scalability）管"量"**——加机器容量涨多少，理想线性；**扩展性（Extensibility）管"变"**——加新业务改不改老代码，理想零修改（架构级开闭原则）。

拿我们那套 MES 打个分（内网企业系统的典型画像）：

| 要素 | 评分 | 依据 |
|---|---|---|
| 性能 | ✔ | 内网量小 + Redis 缓存 + 慢 SQL 监控在岗 |
| 可用性 | ✘ 短板 | 全单点（服务单实例、MySQL/Redis 无副本），硬件一坏停半天 |
| 伸缩性 | △ | 有微服务底子，但无负载均衡、无多实例，加机器无从谈起 |
| 扩展性 | ✔ | 微服务 + 同步 RPC + 事件频道，骨架是好的 |
| 安全性 | △ | 内网隔离 + 统一鉴权护体；外网化那天要补 SSL/限流全套 |

钱都花在了性能和扩展上，可用性和伸缩性欠费——**这不是错，是场景使然**；补票的触发条件是"外网化"和"高可用要求"出现的那天。

## 金句

- 九式是工具箱，五要素是成绩单；**没有度量指标的"我们要高性能"只是口号**
- 集群买可用性，分布式买扩展性——一个靠复制，一个靠拆分
- 缓存挂了不可怕，可怕的是缓存在时数据库很悠闲、缓存没了它接不住
- 服务挂了可以重启，数据丢了无法重生——冗余的优先级高于集群
- 要结果就等（同步），要办事就喊（异步）
- QPS ≈ 并发数 ÷ RT——提吞吐的两条路：加并发、降延迟
