# 同步/异步/并发/并行 + 进程/线程/协程：工程与面试版

> 前置：电商问数第 5 章「基础服务五件套」（问数项目的异步客户端）

## 一句话总纲

**同步/异步是"线程等结果的姿势"，并发/并行是"推进活的方式"，进程/线程/协程是"谁来干活"——三组词各管一层，可自由组合。**

## 两轴四词

- **并发 = 交替推进（单核可），并行 = 真正同时（需多核多机）**。并发应对很多事（吞吐），并行动用很多人（加速比）。互联网后端 90% 考点 = 并发+异步
- **同步/异步 vs 阻塞/非阻塞不能画等号**：阻塞非阻塞=调用卡不卡线程；同步异步=线程等结果的姿势，**同步是线程去等结果，异步是结果出来去找线程，等结果的时候线程可以去处理别的**。四组合都存在：同步阻塞（JDBC）/ **同步非阻塞（NIO Selector 轮询——结果仍自己主动取）** / 异步阻塞（提交后立刻 future.get，白异步）/ 异步非阻塞（await、MQ）

## 贯穿场景：接口查 MySQL + ES + Embedding（各 100ms，互相独立）

| 写法 | 本请求耗时 | 1000 并发所需线程 | 适用 |
|---|---|---|---|
| 同步串行 | 300ms | 1000 | 小流量 |
| 多线程并行(一个线程一个请求，然后一个线程内部gather) | 100ms | 1000 | 传统 Java、并发可控 |
| async 顺序 await | 300ms | **1** | 高并发 I/O 服务 |
| async + gather | 100ms | **1** | 高并发+请求内多路独立 I/O |

**顺序 await = 串行**：await 只决定"等待时让不让线程"，不改代码顺序；单协程内严格串行（语言保证），协程间才交替并发；同协程想并行必须显式 gather。

## Python 异步五件套（谁在执行/谁等待/何时让权）

- `async def` = 定义协程模板；调用得**协程对象（工单）**，一行没跑
- 工单上岗两条路：被 **await**（现场开工并等完）或 **create_task 包成 Task**（登记给事件循环，立刻获得调度资格）
- **事件循环** = 唯一调度员（while 大循环+任务队列）；**await = 让权点**，等待时线程去跑别的协程，结果回来从下一行继续
- **create_task vs gather**：同一机制，零售 vs 批发——create_task 给句柄可分别控制/取消/fire-and-forget；gather 一把派、全完成才继续、结果按序打包
- 裸协程造了没 await = RuntimeWarning "never awaited"，活没干

## 进程/线程/协程

- 进程独立内存 / 线程共享进程内存，均 OS 调度；**协程纯用户态、事件循环调度、协作式（不让权就一直跑）**，KB 级成本
- 关系：1 进程 ≥1 线程；1 线程跑 1 事件循环，内容纳数万协程
- **4 核服务器答案**：核数管"同一时刻几个在算"（并行度 4）；内存管"能开几个"（进程几十~几百/线程几千/协程几万~几十万）；协程管"等待中能挂多少"
- 生产配置：worker 进程数 ≈ 核数（并行吃满 CPU），每进程事件循环扛 I/O 并发

## 阻塞炸弹与载体成本

- **协程里写同步阻塞（requests/time.sleep/同步驱动）= 卡死整个事件循环线程**：该线程上所有请求集体冻结 → 健康检查也卡 → 网关超时重试 → 雪崩。全链路异步是一票否决项（asyncmy/aiohttp/AsyncInferenceClient）
- **Tomcat 模型的天花板**：1 万并发 = 1 万线程 ≈ 10GB 栈内存 + 切换爆炸。**同步模型的瓶颈不是"等"，是"等的人太贵"**
- **Java 虚拟线程（Loom，JDK21）**：同步写法 + 协程级成本，老代码零改造（`spring.threads.virtual.enabled=true`）；无函数染色，可抢占。对标 goroutine 而非 Python 协程

# ***四类异步（在哪异步 + 治什么病）

| 类 | 流程 | 治 | 不治 | 实物 |
|---|---|---|---|---|
| ① 异步 I/O（请求内） | 等结果但不占线程 | 高并发线程耗尽 | 单次延迟、下游故障 | await/FastAPI/WebFlux |
| ② 异步任务（请求外） | 登记给本服务后台执行器，立刻返回 | 轻活不让用户等 | 可靠性（进程重启丢活）、削峰弱 | @Async、BackgroundTasks |
| ③ MQ（服务间） | 消息持久化→立刻返回→消费者慢干+重试+死信 | 等待+下游故障传导+削峰 | 最终一致性变弱、运维成本、必须幂等 | RocketMQ/Kafka |
| ④ 回调/Future 编排 | 组织异步步骤的串联/汇合/异常传播 | 异步代码可读性 | 本身不产生异步 | thenCompose/allOf、await/gather |

**②③本质区别 = 消息是否持久化 + 是否跨进程**：②只敢接"丢了无所谓"的轻活，③才敢接同步金蝶这类重要活。

## 工程选型（依赖定串并，瓶颈定方案）

- I/O 密集（商品详情聚合/问数接口）：异步或虚拟线程；池子按并发量开（等待不占核）
- CPU 密集（APS 排程/批量图片处理）：池子≈核数；Python 走多进程（GIL）；异步零帮助
- 耗时后台任务（重建索引/同步金蝶）：MQ 或独立 worker，与 Web 进程解耦
- 小流量内部系统：直接同步，别为技术而技术（Primer：先看瓶颈）

## 面试高频与追问

- 同步异步 → 结果交付方式 + 工程代价（编排/异常/上下文传递，如 request_id 用 contextvar）
- 异步一定快吗 → 不；单次延迟不变，提升吞吐与资源利用率；单次体验优化走 SSE 流式/缓存/换模型
- 并发并行 → 交替 vs 同时；单核可并发不可并行
- 协程 vs 线程 → 调度者/成本/抢占式 vs 协作式；共享变量在 await 点之间仍可能被别的协程改
- 异步可靠性 → MQ 持久化+确认+重试+幂等+死信
- 易混三句：异步≠并行（单线程可异步）；顺序 await=串行；非阻塞≠异步（轮询=同步非阻塞）

## 实战锚点（本专题三题结论）

1. `a=query("A")` 不 await → 只是工单；输出 B开始→B完成→A开始→A完成（A 未上岗不能插队）
2. 报工同步金蝶超时 5s：方案 A 请求内异步 I/O（省线程不省用户等待）；方案 B MQ 异步化（秒回+故障隔离+削峰，代价最终一致+幂等+死信）——主答案 B
3. LLM 3s+SQL 0.1s 问数接口：只能异步 I/O（依赖定串行、结果必需定不能后台）；瓶颈 97% 在 LLM I/O 等待；单次提速走 SSE 流式/缓存/模型选型
